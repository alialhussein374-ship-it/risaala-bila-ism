# رسالة بلا اسم — علي | Ali

موقع عربي RTL لرسائل مجهولة، مبني بـ HTML/CSS/JavaScript وFirebase Firestore. الرسائل الجديدة تبقى `pending` ولا تظهر للزوار إلا بعد موافقة صاحب الموقع.

## الملفات
- `index.html`: واجهة الموقع ونموذج الرسائل وصندوق الرسائل والإبلاغ.
- `style.css`: التصميم الداكن المتجاوب.
- `app.js`: ربط Firestore وإرسال الرسائل وعرض المنشور منها والإبلاغ.
- `firebase-config.js`: إعدادات Firebase Web (املأها من مشروعك).
- `firestore.rules`: قواعد Firestore الموصى بها.
- `firebase.json`: إعداد نشر قواعد Firestore باستخدام Firebase CLI.

## 1) إعداد Firebase
1. افتح https://console.firebase.google.com/ وأنشئ مشروعًا.
2. من Project settings > General > Your apps، أضف تطبيق Web وانسخ إعداداته.
3. ألصق القيم في `firebase-config.js`. إعدادات Web ليست مفتاح خدمة إدارية، لكن لا تعتمد على إخفائها كحماية؛ قواعد Firestore هي الحماية الأساسية.
4. من Build > Firestore Database أنشئ قاعدة البيانات في وضع الإنتاج.
5. افتح تبويب Rules والصق محتوى `firestore.rules` ثم اضغط Publish.
6. أنشئ مجموعات `messages` و`reports` تلقائيًا عند أول إرسال. لا تفتح القراءة العامة لمجموعة `messages` كلها.

## 2) نشر الموقع على GitHub Pages
1. أنشئ مستودعًا جديدًا على GitHub.
2. ارفع الملفات الخمسة: `index.html`, `style.css`, `app.js`, `firebase-config.js`, `README.md` (يمكن رفع `firestore.rules` و`firebase.json` أيضًا).
3. من Settings > Pages اختر النشر من الفرع `main` والمجلد `/(root)` ثم Save.
4. انتظر رابط GitHub Pages وافتحه على الهاتف. لا تتوقع أن يعمل إرسال الرسائل قبل تعبئة إعدادات Firebase ونشر القواعد.

## 3) مراجعة الرسائل يدويًا
1. افتح Firebase Console > Firestore Database > Data > `messages`.
2. الرسائل الجديدة يكون حقل `status` فيها `pending`.
3. لموافقة رسالة، افتح المستند وغيّر `status` إلى `approved`، ثم أضف `publishedAt` من نوع timestamp (وقت النشر). عند الرفض، احذف المستند أو اتركه pending؛ لن يظهر للزوار.
4. احذف الرسائل المخالفة، وراجع مجموعة `reports` دوريًا. لا تنشر بيانات شخصية أو محتوى تشهيريًا.

## 4) قواعد الإبلاغ
البلاغات تُحفظ في `reports` ولا يمكن قراءتها من الواجهة العامة. راجعها من Firebase Console. صفحة الويب لا تعرض بيانات المبلّغ لأنها لا تطلبها.

## مهم — حدود الخصوصية والحماية
- هذا المشروع لا يطلب اسمًا أو بريدًا أو رقم هاتف من المرسل، ولا يخزّن حقولًا شخصية إضافية في مستند الرسالة.
- لا يمكن ضمان إخفاء الهوية التقنية بالكامل: قد تعالج Google/Firebase بيانات تقنية وفق إعداداتها وسياساتها، كما قد تسجّل خدمات الشبكة معلومات الاتصال.
- قواعد Firestore تمنع الزوار من قراءة الرسائل pending أو تعديل/حذف الرسائل أو قراءة البلاغات، لكنها لا تمنع وحدها الإغراق الآلي (spam). قبل مشاركة الرابط على نطاق واسع، أضف Firebase App Check ووسيلة تحديد معدل إرسال/مراجعة من جهة موثوقة. لا تضع أسرارًا إدارية أو service-account JSON داخل GitHub Pages.
- مفاتيح Firebase Web مخصصة للتطبيق العام، لكن أمان المشروع يعتمد على القواعد، إعدادات Firebase، والحصص والتنبيهات. راقب الاستخدام والتكاليف.
- قواعد Firestore لا تمنع البلاغات المزيفة أو إرسال نص مسيء إلى قائمة الانتظار؛ لذلك تظل المراجعة اليدوية ضرورية.
- إن كنت تريد لوحة إدارة داخل الموقع لاحقًا، استخدم Firebase Authentication مع دور مشرف موثوق وقواعد/وظائف خادم مناسبة؛ لا تضع كلمة سر مشرف ثابتة داخل JavaScript.
